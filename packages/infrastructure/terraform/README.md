# Terraform

Provisions the AWS infrastructure for the orchestrator: a VPC, an ECS Fargate
cluster running all five services, RDS Postgres, Amazon MQ (RabbitMQ), an S3
bucket for uploads, and an ALB with TLS.

## Layout

| File | Contents |
| --- | --- |
| `versions.tf` | Provider and Terraform version constraints |
| `variables.tf` | Inputs, including the per-service sizing map |
| `locals.tf` | Derived names, subnet maths, service→database mapping |
| `network.tf` | VPC, subnets, NAT, routing, S3 gateway endpoint |
| `security-groups.tf` | Least-privilege groups for ALB, tasks, database, broker |
| `data-stores.tf` | RDS, Amazon MQ, uploads bucket |
| `secrets.tf` | Generated secrets in Secrets Manager |
| `iam.tf` | Task execution role and per-service task roles |
| `alb.tf` | ACM certificate, load balancer, listeners, DNS |
| `ecr.tf` | One image repository per service |
| `ecs.tf` | Cluster, task definitions, services |
| `ecs-bootstrap.tf` | Run-once task creating the per-service databases |
| `outputs.tf` | URLs, repository URLs, the bootstrap command |

## First run

State lives in S3. Terraform cannot create the bucket it stores state in, so make
that once per account first — the commands are in `backend.tf`.

```bash
terraform init -backend-config=environments/dev.backend.hcl
terraform plan  -var-file=environments/dev.tfvars
terraform apply -var-file=environments/dev.tfvars
```

`domain_name` and `hosted_zone_id` have no defaults and must point at a Route53
zone you control: the ACM certificate is DNS-validated, so `apply` blocks until
those records resolve.

After the first apply, create the three worker databases. RDS only creates one
database at launch, and the workers each own their own:

```bash
terraform output -raw db_bootstrap_command | bash
```

It runs the same idempotent `CREATE DATABASE ... WHERE NOT EXISTS` that
`docker/init/01-create-service-databases.sh` runs locally, so re-running it after
adding a service is safe.

## Deploying

Images are tagged with the commit SHA — `latest` is only a default for the first
apply. ECR repositories are immutable, so a tag cannot be quietly rewritten.

```bash
aws ecr get-login-password | docker login --username AWS --password-stdin <registry>
docker build -f apps/api/Dockerfile -t <repo>:<sha> .   # context is the repo root
docker push <repo>:<sha>
```

The task definitions target `ARM64` (Graviton — cheaper per vCPU), so build with
`--platform linux/arm64` from an x86 machine.

The frontend bakes `NEXT_PUBLIC_*` into its bundle at build time and needs them
as `--build-arg`, not as task environment variables.

`aws_ecs_service` ignores changes to `task_definition` and `desired_count`, so a
CI deploy that registers a new revision — or an autoscaler — will not be reverted
by the next `terraform apply`.

## What costs money

`environments/dev.tfvars` is sized to be cheap and disposable: one NAT gateway,
a `db.t4g.micro`, no standby, no deletion protection. `prod.tfvars` turns on
multi-AZ, per-AZ NAT gateways and deletion protection.

The NAT gateways are usually the surprise — they bill hourly *and* per GB.
`single_nat_gateway = true` collapses them to one, at the cost of making that
AZ a single point of failure for egress. S3 traffic bypasses NAT entirely via the
gateway endpoint in `network.tf`.

## Security notes

- Nothing running application code sits in a public subnet. The ALB is the only
  internet-facing resource.
- Only the two HTTP services get a target group and a security group rule. The
  three workers take no inbound traffic at all — they consume from RabbitMQ.
- Only the API's task role can reach the uploads bucket. A compromised worker
  cannot read customer documents.
- Secrets are generated by Terraform and injected by the ECS agent, so they are
  not in any image or task definition. **They are in Terraform state in plain
  text** — keep the state bucket private, encrypted and versioned.
- `enable_execute_command` is on, which is how you get a shell in a private-subnet
  task. It is audited via CloudTrail; turn it off in prod if that is not wanted.

## Not covered here

- **CI/CD.** No pipeline is defined; the build and push commands above are manual.
- **Autoscaling.** `desired_count` is fixed. Add `aws_appautoscaling_target` when
  there is load data to size against.
- **WAF, CloudFront.** The ALB is directly internet-facing.
- **Alarms.** Container Insights is enabled and logs ship to CloudWatch, but no
  alarms or dashboards are defined.
